# Token / Presale Due Diligence

Answers "is this mint or presale worth paying for?" with numbers pulled from the chain and from the project's own backend, not from its whitepaper. The deliverable is a verdict the user can act on: skip, free-claim only, or proceed, each backed by a hard figure.

## When to Use

- User drops a mint site, launch page, token address or a "dapet $X kalo ikut" campaign and asks to check it before spending.
- Anything claiming a reward, airdrop, bounty or prize pool in exchange for holding, posting or submitting screenshots.
- Before a paid mint, a "1 USDT per copy" style sale, or an approve-to-a-brand-new-contract flow.
- User drops a marketplace link (Element, OpenSea, Magic Eden) to a young NFT collection and asks "worth it?". Buy-side collection audits follow the same verdict shape but price the exit from the project's own market contract: see `references/nft-collection-audit.md`.
- Also when the site looks clean: the user still needs the two numbers that decide whether the exit is real (raised vs LP depth).
- User asks for the status of a token that already minted ("cek token yg mint dari <project> Fairmint") without asking whether to buy. That is a read-only ledger check, not a purchase audit: report progress, lock state, unlock date and realisable depth, and skip the campaign/approval sections.
- User drops a bare contract address with no site and no stated ask ("coba cek yg ini 0x..."). Identify first, price second: source via Sourcify `?fields=all`, deployer and age from its `deployment` field, the rule set from the config getters, per-wallet lanes by simulation, and only then whether the deal is worth anything. Recipe in `references/contract-recon.md`.
- User drops a bare contract address with only "coba cek ini, ada free mint" and nothing else. That is a read-only lane check, not an audit: resolve the chain, read the free pool and its age (`freeClaimed()` vs `FREE_SHARES()`, `startedAt()`), get the per-wallet gate verdict, then report and ask before signing anything. Skip the site, the campaign backend and the exit math until the user asks about value or a paid lane.
- The user replies "ambil yang free mint aja" / "just do the free claim" after the verdict. The audit is finished; what remains is execution prep, which has its own gating steps below.
- User asks why an executed order never appeared in the Discord execution channel, or asks for every action (mint, buy, sell, transfer, swap) to be logged there. The wiring rule, the standalone poster and the delivery read-back are in "Announcing the Execution" below.
- User questions a lock-up claim or hands over a treasury / multisig address ("emg iya foundation-nya di lock satu tahun? cek multisig ini"). That is a lock verification, not a purchase audit: read the token's own allocation getters, trace where the tokens actually went, then read the lock record and the locker's own source. Recipe in `references/locked-allocation-and-lockers.md`.
- User asks whether a bounce is real demand ("cek di onchain real demand atau bukan?", "nge crash lagi gak atau demand nambah?"). That is a flow question, not a price question: split the window into buyers and sellers, account the native side from the pair's own `Swap` events (never by summing quote-token transfers into the pair, which contract plumbing inflates), and discount the routers and round-trippers before crediting it. Recipe in `references/mint-due-diligence.md` section 16c.
- User drops a project or a whole ecosystem as hype ("lagi rame di grup telegram, cek dong") and it is not a single priced mint: a testnet app with a points program, an app suite, or a pre-mainnet mint whose terms are unpublished. That is reconnaissance plus a setup checklist, not a purchase audit: see `references/ecosystem-and-testnet-recon.md`.
- User asks for a token's off-chain identity ("ada twitter nya gak", "websitenya mana", "siapa timnya") for a mint that is already in a watch list or an alert feed. Bind the site to the contract address and tier every handle as verified / trace-only / none: `references/project-identity-recon.md`.
- User asks "lu bisa dapetin whitelist NFT ini gak?" / "bisa apply WL gak?" for a project whose gate is an off-chain application form (X handle, wallet, social tasks, two written answers) rather than a token holding. That is an off-chain allowlist audit, not a purchase audit: read the form's own route chunk for its exact steps, split the work into what the agent can submit versus what only the user can do, and price the WL against the mint's live public state before calling it worth having. Recipe in `references/ecosystem-and-testnet-recon.md` under "Off-chain whitelist application forms". When the ask is phrased answer-first ("jawab aja dulu, jangan langsung dilakuin"), answer feasibility plus the split and stop; submit nothing.

## Procedure

0. **Resolve the chain before anything else when the user hands over a bare address.** A `0x...` string carries no chain, and DexScreener does not answer it: `/latest/dex/tokens/<addr>` returns `pairs: null` for a fair mint whose pair exists but is unseeded, so a null says nothing about which chain holds the contract. Batch one Python `eth_getCode` per candidate RPC (BSC, Base, Ethereum, Robinhood) and continue on the one with non-empty code. Do not probe chain by chain with a `curl` shell loop: a wrong URL hangs the whole call until timeout while the correct probe takes a second.

1. **Render the page, do not read the description.** Open the URL in the browser, pull `document.body.innerText`, and grep the rendered HTML for `/api/` paths, `fetch(` calls, contract addresses (`0x[a-fA-F0-9]{40}`) and script domains. A raw `curl` of a Vite/React build returns a ~2 kB shell with no content, and on a route-split SPA the main bundle holds no `/api/` path at all: grep it for the lazy route map (`lazy(()=>import("./<Route>-<hash>.js")`) and fetch the chunk for the route you care about (`Whitelist-*.js`, `Mint-*.js`), which is where that page's real steps, endpoints and payload keys sit. The site's own counters (supply, claims, approved users) are marketing until an RPC call or an API response confirms them.
2. **Get the verified source** from Sourcify v2 and read the mint contract end to end, or, when the user hands over a bare address with no site to scrape and no verified source, recover the views from the runtime bytecode: pull the `PUSH4` constants that sit in the dispatch shape (`63<selector>14` and the surrounding jump table), resolve each one by name through `https://api.openchain.xyz/signature-database/v1/lookup?function=0x<selector>` (one GET per selector, `result.function`, since repeating the `function=` param answers HTTP 500; 4byte.directory's `hex_signature` endpoint is the fallback and can answer 403 from this host), then keep only the candidates a live `eth_call` answers with decoded data. This is what surfaces a custom mint contract's own vocabulary (`PRICE()`, `FREE_PER_WALLET()`, `FREE_SUPPLY()`, `freeLeft(address)`, `freeUsed(address)`, `quote(address,uint256)`, `mintOpen()`, `AGENT_ID()`), so the free-lane report is built from the contract's real reads instead of guessed standard names. Read the same address's dependencies out of the bytecode this way too: `AGENT_ID()` returning an address is a contract pointer, and `balanceOf` on it per candidate wallet is the gate read. Look for: price and caps, tokens per share, the payment split, every hardcoded destination (treasury, LP, dead address), and the presence of any owner/admin/withdraw/upgrade path. If no verified source exists at all, say so, then recover the ABI from the site's own inline script before calling the contract unauditable: `grep -n '_ABI = \[' page.html` returns ethers string-array ABIs (`function publicMinted() view returns (uint256)`), which give every view function, event and calldata shape the audit needs. The same script usually also carries a `const ERR = {"0x<selector>": ["message"]}` map, which is the contract's own custom-error table verbatim, plus a constants block with the open timestamp and the caps. Pull those in the same grep: the error table is what turns `eth_estimateGas` into a state probe (see "Executing a Free Claim" step 6).
3. **Read live state over public RPC**: shares minted, paid shares, free mints, deadline, payment-token balance of the mint contract, token `totalSupply`. Reconcile against the site's counter; a mismatch of even a few units means the page is not the ledger.
4. **Verify the gate claim.** If minting requires holding some NFT ("only Agent ID holders"), resolve that contract and call `name()`, `symbol()`, `balanceOf`. A real third-party gate is common and proves nothing about value; a gate the same wallet deployed a day earlier is a red flag. Resolve the gate address from the mint contract itself (`identity()`, `gate()`, `registry()`), never from the site's prompt JSON or docs: those name a raw registry, while the contract usually calls a read-only wrapper that is a different address, and only the wrapper's logic tells you what actually qualifies. Then settle eligibility **per wallet by simulating the mint calldata itself** (`eth_call` with `from` = the candidate address and the exact `mint(n)` bytes): a clean `0x` return means that wallet passes the gate, a custom-error selector (e.g. `0xf947691f`) means it does not, and the selector does not need to be named for the verdict to hold. Quota and price views do not substitute for this and will read as a green light on a wallet that reverts: `freeLeft(addr)` / `freeAvailable(addr)` and `quote(addr, n)` report the quota and the cost of units, not the gate, so a max-quota read plus a zero quote alongside a reverting mint on the same address is the normal shape, not a contradiction. Run it for every lane the user could sign from and report the pass/fail per address.
5. **Run the exit math before repeating any "you get N tokens" line.** Model the pool with the constant-product formula and the fee, seeded only with the LP portion actually collected, then iterate over the number of free claimers. Report how many holders can exit and what the 100th and 500th seller receives. The first seller always looks fine; that is the design.
6. **Check whether the reward pool exists.** Curl the campaign stats endpoint and compare `approved` / `pending` against `paid`. Then read the treasury: balance and `eth_getLogs` on the payment token's `Transfer` topic with the treasury as `from` over recent blocks. Zero outflows plus `paid: 0` while thousands are queued is proof the prize is unfunded.
7. **Confirm the approval scope** from the site's own instructions (exact amount vs unlimited) before saying it is safe to sign, and check whether any step asks for a seed phrase or private key.

8. **Before any signature, prove eligibility and price the gas.** Read `hasAgentId`/`freeAvailable`/`mintedBy` for the *signing* address, estimate gas from that same address, and check the signer lane is actually usable. See "Executing a Free Claim" below.

9. **For an NFT collection, price the exit from the project's own market contract, not the marketplace page.** Resolve the market address from the contract or the site's brief, then enumerate the orderbook yourself: `listedCount()` then `listedIdAt(i)` for every index and `getListing(id)` for seller plus price (the helper names vary; read the ABI you recovered in step 2). Compute the floor, the median, how many asks sit exactly at `MIN_PRICE()`, and the unique-seller count. Then scan the market's `Sale` logs over its whole life for real volume. Zero sales ever is the decisive number, no matter how many listings exist; hundreds of distinct sellers all stacked at the minimum price against a handful of lifetime sales is the same verdict in another shape.

**Start here, it is already scripted.** `scripts/mint_screener.py` runs steps 1-6 end to end and prints the report shape this skill asks for: `audit --url <mint page>` or `audit --ca <token>` (Sourcify flags, live ledger, quote price in USD, LP depth and burn, balance split, per-wallet mint histogram, swap volume with bot concentration, tax-adjusted exit curve), and `discover --blocks N` which finds live launches with no site at all by watching the `Started` / `Minted` / `FreeClaimed` / `Launched` event signatures. Read the output, then verify the one or two numbers the verdict hinges on by hand; do not re-derive the whole thing with ad hoc probes. For a contract's age ("sejak contract live udah berapa jam?"), `scripts/first_event_age.py <rpc_url> <address>` walks the logs backwards in 5000-block chunks, requires several consecutive empty chunks before stopping, and prints the first event's block and timestamp.

## Status Check of an Already-Minted Token

Four reads answer "how is this mint doing", and no browser or site counter is needed:

1. Resolve the mint contract from the user's pointer, then read `token()`, `pair()`, `treasury()`, and the progress counters (`sharesMinted`/`sold`, `paidShares`, `freeMinted`, `deadline`, `mintingOpen()`).
2. Read the token itself: `name`, `symbol`, `decimals`, `totalSupply`, and the transfer-lock flag. `totalSupply` must equal `shares * tokensPerShare`; if it does not, the address is wrong and no other number is worth quoting.
3. Prove the pool state from the pair, not from a flag: `getReserves()` both zero plus LP `totalSupply()` zero means nothing was ever seeded. A `poolOpen() == false` alone does not.
4. Read the asking wallet against the same contract (`hasAgentId`, `mintedBy`, `freeAvailable`) before hinting they can still join; an identity gate with no ID closes the lane regardless of gas.

Report: progress as `minted/total (pct)` and what is left, paid-versus-free split, lock state and deadline in WIB, held payment token against what it can seed, and the open price it implies (open price is normally pinned to mint price, and is hypothetical while transfers revert). Free-share-dominated splits mean a thin pool: say plainly that selling will hit slippage rather than quoting the implied FDV as value.

## Standing Radar (no LLM)

`~/.hermes/scripts/agent_mint_radar.py` runs as a `no_agent: true` cron job (`every 2m`) and costs no model tokens: the scheduler executes the script, delivers stdout verbatim, and an empty stdout sends nothing. It discovers candidates from chain events only (`FreeClaimed(address,bytes32)`, `Minted(address,bytes32,uint256,bytes32)` over the last 2000 blocks), then alerts on three conditions, tuned for claiming the FREE lane rather than reporting its death:

- mint opened inside 90 minutes and the free pool still has >= 25% left (`Mint baru buka, free masih ada`) — the actionable one, carries ETA to empty from the observed claim rate
- free pool dropped under 25% left (`Free pool tinggal X%`)
- paid shares grew >= +1000 inside the last 60 minutes (`Paid jalan cepat`); a first sighting backfills the hour from that contract's own `Minted` logs

Do not alert on "free pool drained": on the FAGENT mint the free pool was 50% gone at 2.34h and 100% gone at 2.85h after `startedAt()`, so a 90%-claimed trigger leaves about ten minutes to act. Alert on the opening instead, and every alert prints a per-wallet eligibility line (`hasAgentId` / gate `identityOf` / gate NFT) because `claimFree()` reverts `NoIdentity` for a wallet without one — an alert nobody can act on is noise.

The script doubles as a probe library: import it with `importlib` to reuse its pure-Python keccak, selector computation, RPC fallback and per-wallet eligibility resolver instead of re-writing `eth_call` plumbing for a one-off check. Recipe and its argument-type pitfall are in `references/mint-due-diligence.md` section 15.

State (`~/.hermes/cache/agent_mint_radar_state.json`) carries per-contract paid and free history plus a dedupe map: the fresh-mint alert fires once per contract per 6h, the low-free heads-up once per 6h, the paid-velocity alert at most once per 3h. Contracts that reach `launched()` are marked done and dropped; a contract whose free pool hits zero stays tracked for the paid watch only. `RADAR_FRESH_S` / `RADAR_LOW_LEFT` / `RADAR_PAID_DELTA` override the thresholds so a test can fire the alert path without waiting for a real mint.

## Before Promising a Free Lane

Three checks decide whether a free-mint watch is worth building at all, and all three come before the cron job.

1. **Measure the drain, then choose the cadence.** Read the mint's own `FreeClaimed` logs, take the first and last claim blocks plus their timestamps, and quote the 50% and 100% times. The free cap is far smaller than the paid cap and usually drains first, so the free lane, not the sellout, is the binding reaction window: on one audited mint it was 50% gone at 2.34h and empty at 2.85h while paid took 8.14h. Answer "akan terkejar?" with that arithmetic and the poll interval it justifies, not with reassurance. Never generalise that hours figure: an agent-gated first-come-first-served cap of 800 slots, one soulbound ID each, emptied in **24 seconds**, so the drain you measure is the only one that sets the cadence, and a seconds-scale window needs the race recipe (`references/mint-due-diligence.md` section 13a) rather than a notification.
2. **Prove the user's own wallet passes the gate before shipping the alert stream.** Call the contract's `identity()` wrapper per wallet and report pass/fail per address. Several sibling projects each deploy their own wrapper but resolve the same handle registry, so a zero from three different gates is evidence about the wallet, not a broken probe. If no wallet passes, say the free lane is closed for them and offer the two real routes (acquire the identity, or watch ungated free mints) instead of delivering alerts that always read not-eligible. Also read the native balance: an eligible wallet with 0 gas cannot execute either.

3. **Price the free allocation's expected value before quoting the gas as a reason to act.** On the sell-out-gated fair mint the pool opens only when the paid cap fills, transfers stay locked until `launched`, and the refund branch invalidates the free allocation (`FreeInvalidated` plus `UnclaimedFreeBurned`). So a free claim's value is conditional on the paid lane finishing, not on eligibility: read `sold()` against `PAID_SHARES` next to the free counter, and when paid sits at zero after hours against a multi-thousand-share target, say the refund outcome is the likely one and the free claim is practice for the calldata rather than a position, even though the gate passes and the gas is cents. Never let a passing `eth_estimateGas` plus a cheap fee stand in for value. Then check whether the free pool can drain inside the window at all: `claims / hours since the first FreeClaimed` against `(FREE_SHARES - freeClaimed)`, and compare the implied drain time with `startedAt + MINT_DURATION - now`. When the implied drain exceeds the time left, say there is no urgency and the deadline is the binding clock, because a free cap that cannot fill makes the countdown meaningless.

Cron minimum interval is one minute; anything faster needs a resident loop, not a job. Never wire a radar into an agent job: at 2 minutes that is 720 LLM sessions a day for output a script can format.

## Executing a Free Claim

The verdict "free claim only" is the start of execution, not permission to sign. Run these in order; each one can end the task.

1. **Find the lane that holds both the gate asset and gas.** Enumerate the signing lanes first (`baw wallet address --json` for the agentic wallet, the derived address of `WALLET_PRIVATE_KEY` for self-custody), then call `balanceOf` on the gate contract per address and read native balance per address and **per chain**: when the gate lives on one network and the mint on another (a BSC Agent ID gating an Ethereum mainnet mint), a wallet holding the gate NFT with 0 ETH on mainnet cannot mint there, and a BSC balance read says nothing about it. The eligible address and the funded address are frequently different wallets; the claim must be sent from the address that holds the gate NFT.
2. **Prove the claim on-chain, do not infer it from the page.** `hasAgentId(addr)` and `freeAvailable(addr)` must both be true, `mintedBy(addr)` zero, and `mintingOpen()` true, and the contract-wide free pool must still have room (`freeClaimed() < freeShares()`). A per-wallet `userInfo(addr).freeClaimed == false` says nothing when the free cap is exhausted: every `claimFree()` then reverts `QuotaExceeded`, so the audit's only live paths are paid shares or skip. Build the free calldata from the contract's own ABI, never from the site's prompt: some fair mints price the free lane through `mint(0)` (zero quantity, zero value), while others expose a separate `claimFree()` and revert a zero-quantity mint with `InvalidAmount`. Quote the exact bytes you intend to send.
3. **Price the gas from the signing address.** `eth_estimateGas` with `from` = signer, the mint target and the calldata; multiply by `eth_gasPrice`; present it in native units and the user's fiat. Ignore any gas limit the site suggests — that is a ceiling, not a quote. A passing estimate is also the cheapest eligibility proof available: `eth_estimateGas` simulates the gate lookup and the whole call, so a `claimFree()` that estimates without revert settles that wallet's identity, quota and cost in one round trip while broadcasting nothing.

   **The agentic wallet offers almost no gas-price control, so plan a gas bump as a post-broadcast action.** `contract-call preview`/`execute` expose only `--gasLimit`: there is no gas-price or gas-level flag, and an undocumented `--gasLevel HIGH` is rejected with `error: unknown option '--gasLevel'` (only `wallet send` takes `--gasLevel LOW|MEDIUM|HIGH`). The one real knob is `baw wallet speed-up <txHash> --level LOW|HIGH` (×1.1 / ×1.25), which resubmits a still-pending tx, so answer a "gas-nya dinaikin aja" request by firing immediately and escalating on a pending read, and say that mechanism out loud instead of implying the fee was set higher up front. `baw wallet gas-price --binanceChainId 56 --json` gives the backend's own low/medium/high reference levels, which can sit an order of magnitude under the public RPC's `eth_gasPrice` suggestion (0.06-0.2 gwei against 1.0 gwei), so quote the receipt's `effectiveGasPrice` afterwards rather than the RPC's number. Budget the CLI itself in any race: each `baw` invocation costs roughly 0.5-0.7 s including node startup, so a preview+execute pair is about 1.2 s of the reaction window and a third round trip is a real handicap.
4. **Gate on signer capability before previewing.** For the Binance agentic wallet, run `baw wallet settings --json` and require `devMode.enabled: true` before any `contract-call preview`. If it is false, hand the user the in-app steps (Agentic Wallet management page → Settings → Developer Mode → read the risk warning → approve the App signature), say the words "tell me when it is on", and end the turn. Do not reroute the claim to a self-custody key that lacks the gate NFT or gas — that trades a two-minute wait for a guaranteed revert.
5. **Restate the lock-up before executing.** Most fair mints make tokens non-transferable until the pool opens and carry a deadline. State the unlock date and that the claim is illiquid until then, so the user cannot mistake a free claim for a $1 balance.
6. **When the free cap is small and the open time is fixed, the race IS the plan (first N claims win).** Do not schedule the claim at the open minute and hand it to a human. Turn the contract's own revert table into a state probe: poll `eth_estimateGas` on the exact claim calldata with `from` = the signing wallet and decode the returned selector against the site's `ERR` map (`NotOpen` / `FreeGone` / `NoIdentity` / `AlreadyClaimed`, versus a clean simulation meaning open **and** eligible **and** room), then fire preview+execute on the first clean read. Ship it as a `no_agent` script scheduled a minute BEFORE the open time so cron's minute granularity and its drift are absorbed by the script's own poll, and give it a hard deadline plus an explicit abort line per state. Note the ordering trap: `NotOpen` is usually checked first, so a pre-open estimate proves nothing about eligibility. Recipe and the env-testable skeleton are in `references/mint-due-diligence.md` section 13a.

Only then preview, show parsed tx plus risk output, and execute on explicit confirmation. A paid share runs the same gate with the payment in `--value`; the calldata, the `balanceChanges` checks and the fee-versus-estimate caveat are in `references/mint-due-diligence.md` section 13.

The two commands, in full, are:

```
baw contract-call preview --binanceChainId 56 \
  --from <agentic wallet> --to <mint contract> \
  --value 0 --inputData <0x selector> --json
baw contract-call execute --requestId <requestId from preview> --json
```

`--from` must be the address that holds the gate NFT, and for this wallet that is the BSC entry of `baw wallet address --json`, not the first entry. Use `--gasLimit` only when the user names one; the backend estimate already covers the gate lookup. A `claimFree()` whose selector estimates clean but whose call reverts at broadcast is almost always the free cap being full contract-wide (`freeClaimed() == FREE_SHARES`), which no per-wallet read shows.

## Exiting: sell from the wallet that holds the tokens

Default to selling from the **same** wallet that received the tokens: one `approve(exact amount)` plus one `swapExactTokensForETHSupportingFeeOnTransferTokens`, both `value: 0`, two transactions total. Generate the calldata with `node ~/.hermes/scripts/agc_swap_calldata.mjs --amount <tokens> --wallet <holder> --slippage-bps 600`, which quotes the router live and prints `approve.data` / `swap.data` / `minOut` / a 10-minute `deadline` for `baw contract-call preview` + `execute`. Regenerate rather than reusing calldata past the deadline.

Only route through a second wallet when the user asks for it, and price that choice: the detour costs two extra transactions (send native gas, move the tokens) and adds a funded second wallet as a new failure point. When a falling price is the reason, say plainly that saving those two transactions is a few cents of gas and does not change the exit value. The transfer itself is untaxed (tax applies to pair transfers), so the detour is safe, just slower and more expensive.

**The same-wallet round trip is proven and costs cents.** A claim plus approve plus swap from the gate-pinned wallet executed as three transactions for 105,941 + 46,044 + 126,872 gas, roughly 0.000038 BNB in total, with the proceeds landing as native in that same wallet. No gas-parking step, no second funded wallet, nothing stranded in an intermediate address. Reach for the detour only for the reasons above, never to save gas: the difference is two transactions, cents on BSC.

**A transfer-tax token delivers less to the pair than the quoted input, so clamp below the quote.** The router quotes against the full `amountIn`, but the token skims its tax on the way to the pair, so the pair receives `amountIn × (1 - tax)` and the payout lands under the quote: a 1,400,000 sell arrived at the pair as 1,372,000 at a 2% tax. Read the executed amount from the pair's own logs and quote that, not the approval size, and keep `amountOutMin` clearly under the quote, since a 100% min-out reverts on the tax alone.

**Attribute the wallet's balance delta before calling it profit.** A claim-then-sell round trip moves three things at once, so `delta = refunded deposit + swap proceeds - total gas`, and proceeds = `delta - refund + gas`, with gas summed as `gasUsed * effectiveGasPrice` over every receipt in the round trip. Quoting the raw delta as the payout double-counts the refunded deposit and under-quotes the sale by the gas.

**Projecting the post-round balance: add the refund for every remaining round, not just the one being sold.** Promising a payout figure off `current balance + final round proceeds` silently drops that round's own deposit refund and reads about 0.01 BNB (roughly $7) short, which the user will catch: the honest projection is `current + refund + proceeds - gas` for each round still to run. Paying the proceeds out to an exchange also needs the deposit address in writing first: it is per network, the agent must never guess or reconstruct it, and the reply should confirm it is the BEP20 (BNB Chain) entry and say that a wrong-network send is unrecoverable. Prove the destination with `eth_getCode` before wiring it into a job (an EOA returns `0x` and can receive, a contract should not be a payout target), read the address back in the reply with its network and wait for an explicit yes, and do not treat nonce 0 plus a zero balance as a wrong-address tell, because a fresh exchange deposit address looks exactly like that. Keep exactly one candidate destination in the job prompt and state in it that the address is never to be substituted, since an unattended run has nobody to ask. Quote the send amount from the live native price at execution time, keep a gas buffer behind, and wire the send as the last step of the final round's job so it runs only after that swap is verified on chain.

Sending gas to the destination wallet is the step that gets skipped and then blocks the approve.

1. Send native gas to the exit wallet before the transfer, leaving >= 0.001 BNB behind for the next day's gas. The destination flag on `baw wallet send` is `--recipient`, not `--to` (`--to` belongs to the `contract-call` family), and native BNB travels through the wrapped-token sentinel in `--tokenAddress`: `baw wallet send --binanceChainId 56 --amount <bnb> --tokenAddress 0xeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee --recipient <dest> --json`. Run `baw wallet send --help` and wire the flags from that output before the command goes into a cron prompt: unlike `contract-call`, `send` has no preview/execute split, so it broadcasts on the first call and a wrong flag stays invisible until the unattended run.
2. Move the balance with a plain `transfer(address,uint256)` (`0xa9059cbb`) via `baw contract-call`, then confirm `balanceOf` on the receiving wallet rose.
3. Swap from the exit lane with the dedicated script (`~/.hermes/scripts/agc_sell_selfcustody.mjs --min-bnb <floor>`): viem plus the self-custody key from the harness `.env`, resolved with `createRequire` against the harness `package.json`. Its exit codes are the contract for anything unattended: `0` sold, `3` no balance (do not retry), `4` swap reverted (retry once, then report), `5` approve/setup failed (report).
4. Clamp `amountOutMin` to roughly 94% of the router quote. `getAmountsOut` does not know the token's transfer tax or the pool fee, so a 100% min-out reverts every sell with a bare router error.

**When the pool does not exist yet, the exit is an event-driven bot, not a scheduled job.** A fair mint's token is untransferable until sell-out, so the exit lane has to be built ahead of time and fired the moment the pool appears. Shape: a resident Python loop under `systemd --user` (cron's one-minute floor cannot trail a 0.45s-block pool), phase A polling `soldOut()` plus the V2 factory's `getPair(token, quote)` for **both** candidate quotes (WBNB and USDT, since the treasury typically seeds only one and the pair address is otherwise unknowable), then phase B reading `getReserves()` at `latest` each poll, folding the pair's own `Swap` events into a net quote-flow figure, and trailing the **executable** exit value rather than the mid price. Three things matter more than the constants: the trailing width comes from the realised variance of that exit-value series rather than a hand-picked percentage; the net-flow sign is the regime signal (three consecutive outflow windows mean the pool is being sold into, so exit instead of waiting for a bounce); and there is a time cap, because the first sellers are the only ones a thin pool can pay. Two constraints on the implementation: express any break-even floor in the **executable exit value** (`exit ≈ quote_reserve × (amountIn × (1 - pool_fee)) / (token_reserve + amountIn × (1 - pool_fee))`), never in pool-quote-reserve terms, because a reserve-denominated threshold silently changes meaning when the quote side is BNB rather than USDT (naming such a flag `--be-floor-usdt` while comparing it against a USD exit value is the same unit error in the argument list); and give the unit file an explicit `PATH` covering the CLI's node bin, `node` and `curl`, plus an interpreter that actually has the keccak library, since a `systemd --user` unit inherits neither the login shell's PATH nor the agent's virtualenv. A trailing stop is also not a price target: it can only ever fill at the peak minus its width, so when the user asks "at what price does it sell?" answer that the trigger is the retrace off the high-water mark plus the flow/depth/time overrides, and that a rising price raises the mark and delays the sale rather than tripping it.

**Validate a first-time swap leg before the asset exists.** Four checks, no funds needed: derive the wallet address from the key and confirm it matches the lane you meant; run the script once to exercise the zero-balance guard and its exit code; quote live reserves through `getAmountsOut`; then `eth_call` the exact calldata with `from` set to any large holder of the token (no key needed). A decoded `TransferHelper: TRANSFER_FROM_FAILED` proves the selector and argument encoding are correct, because a wrong encoding reverts with a bare `0x` and reads as a broken contract. Report which legs remain unproven instead of calling the path tested.

## Announcing the Execution (Discord order log)

Every order the agent actually executes must announce itself in the execution channel (`#order-execution`); an order that ran but never posted is an unlogged order, so the alert is part of the execution, not a report about it.

- **Paths that broadcast themselves.** Orders signed through the web3 harness MCP tools (`execute_signed_tx`, `execute_autonomous_sell`, `execute_baw_agentic_trade`) already post via `webhook.ts::broadcastToDiscord`, which also routes buys/mints to the positions channel and sells to positions plus pnl. Pass the real action to the prepare step, because the label comes from what was staged: the harness action enum accepts `BUY, MINT, CLAIM, SELL, AUTO_SELL, EMERGENCY_SELL, TRANSFER, SWAP, APPROVE, LP_ADD, LP_REMOVE, CONTRACT_CALL`, so widening it is what stops a transfer or an approve from being logged as a buy.
- **Paths that do not: post it yourself.** A direct `baw contract-call`, a viem probe script, a manual claim/sell/transfer or a cron job broadcasts nothing, so call the standalone poster: `python3 ~/.hermes/scripts/order_alert.py --action MINT|BUY|SELL|SWAP|TRANSFER|CLAIM|APPROVE|LP_ADD|LP_REMOVE|CONTRACT_CALL --chain BSC --asset "<token> · <what>" --value "0.0100 BNB" --contract 0x.. --tx 0x.. --source <lane> --note "POSITION=.." --also positions,pnl`. `--dry-run` prints the embed, `--check` prints which webhooks resolved, and a failed post exits 1 so a cron job surfaces the failure instead of going quiet. Post with `curl` (Discord answers Cloudflare `error code: 1010` to Python `urllib`). Any cron job that executes an order must carry the alert as a required step in its prompt and report the HTTP code it got.
- **Verify a webhook post with `?wait=true`, never by reading the channel back.** With `--wait`, Discord returns the created message object (`HTTP 200` plus the message `id`), which is the only read-back a webhook offers; quote that id as the proof of delivery. A bot REST message-list call can be refused for this host (`40333 internal network error`) while the webhook and `/users/@me` work fine, so a failed channel read proves nothing about whether the alert landed. Prefer `--wait` on the next real order over posting a marker line, and if a marker line did go into the channel, say so in the report so the user can delete it.
- The poster's colour map mirrors `ACTION_COLORS` in `~/.hermes/web3-harness/src/webhook.ts`; change both together, and remember the harness only picks up its copy when the MCP server respawns.

## After the Claim: Verify, Then Watch

A broadcast is not a confirmed receipt, and a preview is not a broadcast. Close the loop in this order.

1. **Say which state you are in.** `contract-call preview` only simulates and returns a `requestId`; no transaction exists and there is no hash to report. Once `contract-call execute` returns `status: BROADCASTED` with a `txHash`, then verify and quote the hash.
2. **Verify from the chain, not from the CLI status.** `eth_getTransactionReceipt` for `status: 0x1`, `gasUsed * effectiveGasPrice` for the real fee, then re-read the token `balanceOf` and the mint counter (`sharesMinted`) to prove the delta landed. Report hash, block, fee, and new balance together. For an unattended job, also confirm the job itself fired and reconcile it against the chain separately: `cronjob_manage` has no `get` action, so call `action=list` and read that job's `last_run_at`, `last_status` and `state`. A job reporting `ok` and a chain that actually moved are two facts, and the receipt is the one that counts.

   **Price a past round from the wallet's own `tx-history`, not from historical pool state.** `baw wallet tx-history --binanceChainId 56 --json` returns each entry's `txType` (`swap`, `approve`, `contract_call`, `transfer`, `mint`) with `instructions.send` / `instructions.receive` carrying the exact amounts and `networkFee.feeValue` in wei, so a completed round's proceeds and per-tx fees come out with no archive node and no log decoding. Reach for it when a historical `getReserves()` is refused (`not supported`) and when a `Swap`-topic scan of the pair returns zero rows for a sell the token's own `Transfer` logs prove happened: the scan is mis-filtered, the swap is not missing. For a price or depth history across a window, read the pair's `Sync` events (`0x1c411e9a…`, two reserve words per row) and count the rows, since that survives the same historical-state refusal that blocks an old-block `getReserves()`.
3. **Explain an "empty" history before troubleshooting it.** Devices' Orders pages list trading orders only (market, limit, prediction). A Developer-Mode `contract-call` never appears there; it shows in the transaction/activity history as `txType: contract_call`. Say that instead of hunting a phantom bug.
4. **Schedule the deadline report as a `no_agent` script, not an agent job.** When the user asks to be told before the mint window closes, write one Python script that reads the mint's own views (`info()`, `launched()`, pair `getReserves()`, token `balanceOf`) and prints a fixed-format Indonesian report plus a verdict line, then create two one-shot jobs from it: one about an hour before the deadline and one just after it for the actual outcome (pool opened versus free allocation burned). Schedule with an absolute ISO timestamp and confirm the returned `next_run_at` carries the WIB offset, because a schedule expression is wall clock and a wrong offset fires an hour off. Pin `startedAt` as a constant in the script rather than re-deriving elapsed time from a guessed start block, and cap the computed sellout ETA: a pace of 0.07 shares/hour against a 10,000 cap yields a six-figure hour count, which is noise rather than a number, so compare the ETA against the window and print the refund branch instead.

5. **Schedule the unlock watch only after the claim confirms.** One-shot job a minute after the pool deadline, then a short recurring job (every 15 minutes for a couple of hours) that reads `poolOpen()`, pair reserves, spot price, LP depth and the modelled sell-out. Default to report-only; auto-sell only if the user states an explicit price or value threshold. Once the deadline passes, opening is permissionless, so the pool will open without you calling `openPool()` yourself.

6. **Schedule the claim off each position's own mint timestamp, never off a round hour the user names.** `claimFree` walks positions in creation order and breaks at the first one younger than the lane's `REFUND_DELAY`, so a job that fires earlier than `mint time + REFUND_DELAY` claims the older position and silently leaves the newer one behind while still reporting success. When two positions were minted hours apart on the same WIB day (one before and one after the 07:00 WIB quota roll), set the claim a few minutes after the LAST of them matures so both clear in one transaction, and say in the reply why the requested hour moved instead of quietly rescheduling it.
7. **Shape the unattended daily routine as independent steps, each with its own alert.** Mint, claim and sell belong in one job only if a failure in one cannot abort the others: state that in the prompt, post a separate `order_alert.py` alert per step, and have the report carry the step name, tx hash and HTTP code per step plus one closing verdict line (tokens sold, native received, balance left per wallet). A first-ever leg is allowed to fail loudly; bound it with a retry count and a min-proceeds floor passed as script arguments rather than letting the job improvise a different route mid-run.

**A refund branch only pays if the signing lane is allowed to call it; diagnose the two sides separately.** Once `phase()` reaches Refunds the payout is permissionless code, but somebody still has to sign it, and a wallet-level veto is not the project withholding money. When `baw contract-call preview` is refused with `351803 ... risk is too high and has been rejected: blocked`, prove the split instead of asserting it: (1) `eth_call` the exact calldata from the same wallet on a public RPC, because a clean read-only call means the contract path is open and no risk engine is involved; (2) reconcile the contract's own books, `quoteToken.balanceOf(mint)` against `(sold - refundedShares) * price`, to show every outstanding share is funded; (3) scan the `Refunded` topic for other payers who already got the same amount, which converts "proyeknya nipu" into "our lane is blocked" with a number the user can check. Never reroute the call to another wallet: paid shares and positions are keyed to the address that minted, so a different lane reverts (`InvalidAmount`, zero shares) or refunds nothing. Report which side is blocking, say whether the refund carries a deadline (when it does not, waiting costs the user nothing), and name the two real routes: the App-side `abnormalTxnHandling` setting, which converts the veto into a `PENDING_CONFIRMATION` the user approves in the Binance App (section 18 of `references/mint-due-diligence.md`), and a support ticket. Never offer "refund it manually from the App" as a workaround before checking that setting: the App cannot compose calldata, so there is no button to press and the answer wastes the user's trust.

**Watch a blocked lane with a deterministic probe under `monitor`, not a recurring agent job.** Put the probe in `~/.hermes/scripts/` (it attempts the `contract-call preview` and prints exactly one stable token, `READY` or `BLOCKED:<code>`, with no timestamps) and create the job with `monitor: <filename>` so the scheduler hashes the output and only wakes the agent when it changes: a status that stays blocked costs nothing and the first unblocked tick delivers one message. Pass the bare filename, since `monitor` and `script` resolve relative to `~/.hermes/scripts/` and reject an absolute path. Keep the job report-only and put the go-ahead request in that message, because an unattended tick cannot ask a question and the user is the one who authorizes a signature he has not seen.

**Patch the scheduled job in place when the plan changes, and never leave a step the user cancelled.** When the user cuts part of an agreed ladder after the jobs exist ("gausah mint lagi yg 4,3,1 share"), rewrite that job's prompt to delete the cancelled step and state the prohibition explicitly ("no `mintFree`, no quota read, no BNB to the minter, claim and sell only"), then confirm the returned `next_run_at` is unchanged and say which step was removed. Deleting the job throws away the claim that is still wanted; leaving it un-patched mints a quota the user just cancelled, because the prompt is the only place that constraint survives into an unattended run.

**Two claim shapes are legitimate; offer both instead of silently choosing.** One job a few minutes after the LAST position matures clears every matured position in a single tx (cheapest, and what `claimFree` with empty ids does anyway), or one job per position so the earlier one exits hours sooner. Quote the difference (a second exit run costs one more `baw wallet send` parking ~0.002 BNB in the exit lane) and default to the split when the price is falling and each position's value is decaying while it waits.

**Check the wallet session outlives the event before promising an unattended send.** `baw wallet settings --json` reports `sessionExpireTime`, `inactiveSignOutTime`, `signInMaxTime` and `maxSigninDuration` (48h); `baw auth signin` only prints a QR that the user scans in the Wallet App, so it cannot be renewed by the agent. If the session expires before the deadline, the job must be report-only and the user must be told to scan once before the window (one sign-in covers up to 48h). Say that up front, not when the job fails.
5. **Do not imply waiting raises the price.** When the LP is seeded at `LP_TOKENS_PER_PAID` per paid share against the LP split, the open price is pinned to the mint price by construction. Say plainly that a higher price requires buyers, not time, so a "wait for a good price" plan is really a "hope a buyer shows up" plan.

Commands for receipt verification and the `tx-history` shape are in `references/mint-due-diligence.md`; section 18 covers the refund branch and how to prove a payout the signing lane is blocked from sending.

## Confirming Which Wallet Participated

When the user asks "wallet mana yang kita mint kemarin?", it is almost always because a reward form, campaign page or proof upload wants an address. Answer from the chain and the recorded tx, never from memory or from the wallet app's order list.

1. Re-read per lane: `balanceOf(token)` on the token, `mintedBy` / `paidBy` / `hasAgentId` / `freeAvailable` on the mint contract, for the agentic wallet address (`baw wallet address --json`) and the self-custody address (derived from `WALLET_PRIVATE_KEY`). `mintedBy > 0` identifies the participant; a lane with `hasAgentId: false` could never have minted, so a zero there is structural, not a bad read.
2. Re-verify the specific tx with `eth_getTransactionReceipt` (status, block, `from`) before quoting its hash, then quote hash + block + token balance together.
3. Compare the address the user is about to submit against the address that actually holds the token, and say match or mismatch out loud. A campaign that asks for a wallet-ownership screenshot *and* a payout address only pays the wallet that holds the asset; an approved submission against a different address is the thing to flag first.
4. An "approved, waiting for disbursement" page state is a review verdict, not a payment. Do not read it as funds received unless a transfer is visible on the payment token.

## Verdict Rules

- **Separate theft risk from economic risk.** "No drainer, no seed-phrase request, approve is capped" clears only the theft question. It says nothing about whether the token is worth buying, so never let it end the report.
- **Quote two figures every time:** what was actually raised in the payment token, and how much of it reaches the LP. A project that raised 300 USDT and seeds a 210 USDT pool cannot pay out a 10,000 USDT campaign.
- **Reward bigger than the user's realisable exit is a shill task, not a prize.** When the bounty exceeds what a holder can actually withdraw, name that explicitly.
- **A reward that requires public posting plus wallet address plus screenshots is an engagement farm.** Say it plainly, and note that manual review with no on-chain payouts means nothing will be paid.
- **Credit what is genuinely clean.** Verified source, no admin, bounded approve, funded pool, real payouts: say so without hedging. A mixed verdict is the normal result, not a cowardly one.
- **A sold-out mint is a distribution win, not an exit.** Confirm the sellout from the counters (`sold() == MAX_SHARES`, `freeClaimed()`, `launched`), then say what it is worth: raise versus LP depth, and the full-cohort exit as a share of what holders paid. A mint that filled in hours with a thousand-plus payers can still leave the cohort recovering roughly half of entry, and that sentence is the one the user needs.
- **Price the payment token before quoting any fiat figure.** When the raise is denominated in the project's own token, every USD number rides that token's own pool: read its stable pair, and quote its FDV-versus-liquidity ratio, because a $60M FDV on a $0.5M pool means the dollars are not withdrawable at that price. Never present a fiat total while the quote token is unpriced.
- **A refundable-deposit free lane is free of contract risk, not of price risk; answer "kok ini free money?" with two numbers.** First verify the deposit has no hole (the minter's native balance must equal its own `refundOwed()` counter to the wei), then price the whole future emission against the pool: an emission sized to consume the remaining supply cap can be many multiples of the pool's entire token reserve, and the pool's whole quote side is the ceiling on what every seller combined can ever withdraw. Skip the second number and the report reads as an endorsement of a yield that exists only at today's price. When quoting the net figure, deduct the sell tax, the pool fee and gas, and never the deposit: it is returned in full, so counting it as a cost under-quotes the lane by the deposit itself and the user will ask why the number sits 20% under the payout. Never quote a break-even price per position either: with the deposit refunded the only cost is gas, so every cent of the sale proceeds is profit, and a "titik impas di $X per posisi" line is the same deposit-as-cost error wearing a different hat, which the user will then use to decide whether to exit.
- **Quote the valuation the asking price implies, not just the price.** `(mint price × units) ÷ (fraction of total supply promised)` is the FDV the seller is setting: a $25 mint for a collection promised 10% of a 1B supply implies roughly a $375k FDV. State it, because it is usually the smallest number in the report and it answers "is this cheap?" without endorsing the price.
- **An unlocked allocation on a thin pool outweighs every clean signal.** A verified contract with no admin path can still carry an allocation worth several times the pair's entire token reserve, so read the token's own `foundation()` / `marketing()` / `opsWallet()` addresses and say which of them are locked and which are not. When a lock claim checks out, state the mechanism that enforces it (the locker function and its time condition), the unlock date in the user's timezone, and who holds the unlock key; when it does not check out, that finding leads the report even if everything else is clean.
- **A promised LP seed from outside the contract has no address, no enforcement, and no entry in the code; price it as a scenario and name the trigger that would verify it.** When a fair mint says the treasury will add the raised funds plus an extra native amount ("kami tambah 15 BNB") to the pool, the open price the user is shown is a formula on that promise: `(raise + promised native at the live native price) / LP tokens`. Report the allocation's value under both branches (promise honoured versus only the raise seeded) and mark it unenforceable, because it lives in the whitepaper, not in `_sellOut()`. To answer "wallet mana yang nambahin BNB-nya?" read the named treasury's live native balance and `eth_getTransactionCount` (an EOA sitting near zero means the native is not parked yet) and say the only verifiable signal is the `SoldOut` event plus the pool creation afterwards; note the treasury's own mint participation (`mintedBy` / `paidBy`) as a soft signal. The extra native lifts the open price only if a buyer takes the other side, and the pool's whole quote side is still the ceiling on what every seller combined can withdraw.
- **Never endorse the token price.** The output is a risk verdict plus a recommended action, not a price target.

## Pitfalls

- **The site's counters can be stale or hardcoded.** Always recompute supply from `totalSupply` and the minted/paid counters; the leaderboard and "X/Y minted" text can drift by tens of units or be static markup.
- **A node that serves a block can still answer `[]` for it.** `bsc-rpc.publicnode.com` returns an empty log set for ranges it does not serve (a block holding a known `Minted` event came back `[]`), which reads as a short mint. Never trust a log scan that has no cross-check: reconcile `sum(Minted.shares)` against the contract's `sold()` and `len(FreeClaimed)` against `freeClaimed()`, and widen the start block until they match. A scan landing 1,000 shares below `sold()` is a bad range, not a partial sellout.
- **Fixed `latest - N` windows understate participation.** The identity quota opens before the first paid mint and free claims can run earlier than any paid one, so the first events sit below a guessed start block. Widen backwards until the counters reconcile.
- **A refundable mint's counters run backwards, so every sell-out ETA must be net of refunds.** When the contract lets a paid minter call `refund()` at any time before sell-out, that call burns the paid shares and decrements `paidShares` and `sharesMinted`, so both counters fall while paid mints keep landing: `sharesMinted 10626 -> 10588` and `paidShares 2926 -> 2850` within minutes, with the "shares remaining" figure growing instead of shrinking. A pace derived from `Minted` events alone is then structurally optimistic, and a rate you took minutes earlier can be the opposite sign by the time the user reads it. Measure net over a multi-chunk window or two `paidShares` reads a couple of minutes apart, scan the contract's `Refunded` topic to confirm the drop is refunds rather than a bad read, and when net is negative say the sell-out is receding and the refund branch is the live outcome (a free option: the capital returns, only gas is spent). Retract the earlier figure explicitly when the net flips instead of quietly restating it.
- **Tally refunds per wallet before calling a refund wave collapsing conviction.** Group the `Refunded` rows by wallet and read the share-count distribution: on one lane 63 of 81 refunding wallets refunded exactly `BASE_QUOTA` (7) in a single call while the rest were scattered (1, 2, 4, 8, 10, 20). An all-at-the-base-quota cluster is the signature of quota-filling scripts unwinding, which is weaker evidence about a project's value than a broad scatter of retail sizes would be, so say "script wallets unwinding" rather than "buyers are dumping". Name the second driver too: the free-share bonus is granted only on a wallet's first mint *while the free cap still has room*, so once the free pool is exhausted a paid mint buys tokens with nothing attached and the sell-out is the only remaining catalyst, and a zero-cost exit plus a dead catalyst is what turns a late-stage mint into a revolving door.
- **On this fair-mint template the team can force the sell-out for nearly free, so "will it fill?" is a team decision, not a market one.** `_sellOut()` forwards the contract's entire held balance (`usdt.balanceOf(this)` plus `address(this).balance`) to the project's own treasury, so the team minting the remaining paid shares pays itself back inside the sell-out transaction: net cost is gas, and it collects the paid tokens plus the LP allocation on top. When the remaining quota is a few hundred shares and the held funds already belong to the treasury, never imply the market will eventually clear it; state that the project can close it whenever it chooses, and note that a counter visibly moving backwards makes that less likely, not more.
- **Do not date a contract's launch off the first empty log chunk.** A deployed contract emits nothing, so its first event is the earliest on-chain date you can get, but sparse activity (one event per 5000-block chunk, normal far from the launch burst) leaves plenty of empty chunks ABOVE the real start, so stopping at the first empty one understates the age by hours. Walk back requiring several consecutive empty chunks (or probe coarse chunks first to bracket the boundary), then take the oldest chunk holding a hit and read its minimum block timestamp. Explorers are not a shortcut from a datacenter host (BscScan serves a Cloudflare challenge) and a historical `eth_getCode` answers `not supported` / `header not found` on the free nodes, so the log walk is the only route. `scripts/first_event_age.py` does this walk.
- **An empty claim-event scan in the first 24h of a refundable-deposit lane is structural, not silence.** `claimFree` reverts until `position.time + REFUND_DELAY`, so the `ClaimFree` topic legitimately returns zero rows while deposits are already flowing in. Read `refundOwed` and the position counters instead of reporting a dead project, and quote the exit clock per position (mint timestamp + delay), never as the trading-open time, because two positions opened hours apart exit hours apart.
- **A project's own agent docs describe the claim loop loosely; the contract's loop is the spec.** `llms.txt` said positions younger than the delay are "skipped, not reverted", but `claimFree` with empty `ids` **breaks** at the first unmatured position (only explicit ids `continue` past one), so everything after it waits for the next call and the cursor stops there. Read the loop in the source before scheduling claims: the "skipped" reading produces a one-job plan that silently leaves the second position behind while reporting success.
- **A green `claimFree([])` simulation is not evidence that anything is claimable.** With nothing matured the empty-ids branch scans, finds `count == 0` and returns without reverting, so `eth_call` answers `0x` and `eth_estimateGas` succeeds; only a non-zero `pending(addr)` separates "nothing matured" from "claim will work". Gate the decision on `pending(addr)` plus the per-position maturity clock, never on the simulation, because "estimates clean" is the same answer in both states, and an unattended job built on it reports success having claimed nothing.
- **The paid count, not the wallet count, tells you the raise.** Free mints inflate supply enormously; the LP is funded only by paid shares. Compute LP size from paid shares and the LP split, never from total mints.
- **Free mint plus thin LP makes the user the exit liquidity.** The first seller gets roughly the mint price; by the few-hundredth seller the payout rounds to cents. Show the curve rather than the headline "$1 per share".
- **`hashlib.sha3_256` is not Keccak.** Selectors computed with the hashlib SHA3 module are wrong and every call reverts with a bare `execution reverted: 0x`, which reads like a broken contract instead of a broken probe. Compute with `Crypto.Hash.keccak` (or take the selector straight from the bytecode `63<selector>` constants and from the site's own ABI list) before concluding anything.
- **`str(n)` into a hex padder encodes the decimal digits as hex.** An address-orientated `pad()` (`a.lower().replace('0x','').rjust(64,'0')`) turns the decimal string `10000` into `0x10000` = 65,536, so every numeric `eth_call` argument silently queries a different index and a documented flat-then-step price ladder reads as 9x steeper than the verified source. Encode integers as `f'{n:064x}'`, and sanity-check one point whose answer is already known (tier-1 price, share #1) before trusting any ladder, quota or curve read.
- **When on-chain reads contradict an `exact_match` verified source, suspect the probe before the source.** Two RPC providers agreeing does not catch this, because a mis-encoded call is mis-encoded on every node; neither does re-deriving the same numbers with the same helper. Settle it against the deployed bytecode: find the dispatch entry (`63<selector>1461<dest>57`), read `dest`, disassemble the body and check the constants the source claims. Recipe in `references/mint-due-diligence.md` section 17.
- **An unverified contract may still document itself.** Before calling it unauditable, fetch `/skill.md`, `/agent-brief.txt`, `/mcp.json`, `/llms.txt`, `/abi.json` at the site root: agent-facing projects publish their full selector table, error strings, events and constants there, and a project aimed at agent wallets often publishes its entire daily operating routine as a `skill.md` (exact calldata per action, the 4-byte error table, the preflight commands). Verified-source absence is a risk statement, not the end of the audit.
- **A 200 on those agent files can be the SPA catch-all.** On Cloudflare Pages every path returns the index HTML with status 200, so a successful curl proves nothing: check the body starts with `<!DOCTYPE` (or the content-type is `text/html`) and treat it as absent, then fall back to the inline-script ABI.
- **Marketplace indexers lie about new collections.** A listing page can show `Items 0`, no floor, no holders and "Content not available yet" while the chain already holds thousands of minted pieces and dozens of live asks. Never quote marketplace stats as the ledger; read the collection and its market contract over RPC and use the marketplace only for its orderbook (bids, collection offers).
- **`totalSupply` on an ERC721 usually does not exist.** An `0x` return means unsupported, not zero supply; verify with `name`/`symbol` and `balanceOf` instead.
- **A public immutable's getter is config, not a lane, and its small integer return is not a status code.** `freeAi()` answering `2` and `freeV2()` answering `4` are the free allowances for the .ai and whitelist paths, not mint states; read as statuses they invent branches that do not exist and bury the real one (`claimFree(proof)` with `[]` for an Agent-ID holder). Read the source before interpreting any scalar return from a function whose name matches a constructor parameter, and simulate only the functions with side semantics.
- **Sourcify's `deployment` field gives the deploy block and deployer for free.** `GET /server/v2/contract/{chainId}/{address}?fields=all` returns `deployment.transactionHash / blockNumber / deployer`, so an `eth_getCode` bisect is unnecessary for a verified contract, and the deployer address is what settles lineage (deployer == feeRecipient == the known project's creator) instead of guessing from a reused name and `baseURI`.
- **Decode address returns from the padded word, not from the decimal value.** Take the last 40 hex chars and confirm by calling `name()` on the result; a bad decode points confidently at an unrelated contract.
- **Sourcify v1 endpoints are gone.** `/server/repository/...` and `/contracts/full_match/...` return a JSON 404 notice; use `/server/v2/contract/{chainId}/{address}?fields=sources,abi`.
- **The source JSON contains raw control characters.** Parse with `json.loads(raw, strict=False)` or it dies with `Invalid control character`.
- **Do not submit test entries to a campaign backend** to see how it behaves. Read its stats endpoint; never fabricate submissions, screenshots or wallet addresses.
- **The wallet that is eligible is not necessarily the wallet that can sign.** Agentic wallet and self-custody key are separate addresses with separate balances and separate NFTs; check the gate asset per address instead of assuming the connected wallet is the right one.
- **A site's agent prompt is a call template, not an ABI.** Pages that hand you a ready JSON prompt name the function, the args and sometimes the wrong gate address; every field still has to be confirmed against the verified ABI and the contract's own views, because a zero-quantity mint or a registry address that is not the gate reverts only at broadcast time.
- **`351803` and `351805` are different failures and only one of them is the contract's fault.** `351803` "Transaction risk is too high and has been rejected: blocked" is the risk engine refusing to sign for that destination contract before anything is simulated, while `351805` "Transaction simulation failed: execution reverted" is the contract itself rejecting the call (closed mint phase, drained free cap). Tell them apart with a control call: preview a harmless call to an unrelated verified contract (a `balanceOf` on WBNB) to show the session and Dev Mode are healthy, and re-preview the same destination once its phase changed. Do not call a `351803` permanent: the same byte-identical preview was refused once and then returned a clean `requestId` (with `requireConfirmation: true`) on a re-run minutes later, so re-run the preview once or twice before concluding, then fall back to the `abnormalTxnHandling` setting. Reporting it as "the project refuses to pay" is wrong when an `eth_call` of the same calldata succeeds. After a refund that burns a position the exit bot was watching, disable that bot (`systemctl --user disable --now <unit>`) once the receipt is confirmed, not before, since a user who never taps the App approval still holds the position.
- **Developer Mode being off is a user-side gate, not a tool failure.** The fix is enabling it in the Binance App (7-day validity, each use extends it), and the correct move is to state the steps and wait — never to sign the same call from another lane that fails the gate check.
- **A preview's `balanceChanges` entry carries a magnitude, not a direction.** A `claimFree()` preview reported `change: 5e+25` for a call that gains 50M tokens, with no sign field to read; the same field is positive for a token the wallet is about to lose. Treat it as "this token moves" and prove the direction afterwards with `balanceOf` on the token contract, which also gives the number to quote.
- **A preview is not a broadcast.** It simulates and hands back a `requestId`; nothing is on chain and no `txHash` exists. Never let the user go looking for a transaction that only ever previewed, and never present a preview as done.
- **Order History is trading orders, not contract calls.** A Developer-Mode call appears as `txType: contract_call` in `baw wallet tx-history --binanceChainId 56`; the App's Orders page shows market/limit/prediction orders only, so an empty Orders list after a successful mint is expected. Note also that `tx-history` rejects `--limit` with `unknown option`; page it with the cursor flags instead of retrying.
- **Never auto-sell on a vague "kalau harganya tinggi".** A scheduled job cannot ask questions, so ask for the threshold once, in chat, before writing the job; otherwise make the job report-only and say you are waiting for the order.
- **A free claim is free of payment, not free of cost or risk.** It still costs gas, still requires the gate asset, and yields a token that may not be transferable for days. Say both before asking for the signature.
- **Answer "kapan bisa refund?" from the contract's own `require` list, not from a date.** A fair mint's `refund()` is normally gated only on a state flag plus a per-wallet counter (`require(!soldOut)` and `paidBy[msg.sender] > 0`), so there is no deadline by design and the honest clock is the sell-out event. Quote the three things together: the refund window, the per-wallet keying (only the paying address can call it, another lane refunds nothing), and the sell-out ETA, and say plainly that sell-out closes refund permanently.
- **"Hold N+ NFTs to qualify for the token" with no token contract is the bait, not the value.** Price it: N times the floor is the real ask, and the verdict line is that the allocation has no contract, no snapshot and no announced supply. Sweep it into the same bucket as a prize pool whose treasury shows zero outflows.
- **"GTD" / "WL" is a guaranteed allocation, not a free mint.** Quote the tier price out loud and say the tiers usually cost the same, because the common misread is that a whitelist spot means a free mint; a guaranteed slot at $X is not free.
- **A proof-of-work mint is a hardware gate, not a free mint.** "Free, no price" can hide a `keccak256(salt||sender||nonce) <= target` gate or a leading-zero `difficultyBits()` ladder, where expected work is `2^bits` doubling per step. Benchmark keccak on the actual host (a 2-core VPS is ~145k-900k H/s, a GPU is 3-4 orders faster) and quote the live difficulty plus the breakpoints before saying anyone can mint. Arithmetic per shape is in `references/nft-collection-audit.md`.
- **Public BSC RPC caps `eth_getLogs` ranges and answers `limit exceeded`.** `bsc-dataseed*.binance.org` / `defibit` reject even a 100-block query with `{"code":-32005,"message":"limit exceeded"}`, `1rpc` caps at 50 blocks, and some nodes want 25. Use `https://rpc-bsc.48.club` (1500-5000-block chunks work, `User-Agent: Mozilla/5.0`; it rejects larger ranges with `exceed maximum block range: 5000`), check the `error` key per chunk, and print the failed-chunk count: a loop that swallows the error returns zero events, which reads as "nothing happened on chain". An empty log set from one node is unverified, never proof.
- **The same public nodes answer `eth_call` only at `latest`.** Reading the pair's reserves or a wallet's `balanceOf` at a historical block tag returns no `result` on `rpc-bsc.48.club`, so a window's reserve delta cannot be read out of state at all; the retry against another provider wastes minutes before failing the same way. `eth_getCode` behaves the same way, and worse: old blocks answer `header not found` while recent ones are served from the tip, so a **binary search for a contract's deployment block converges on `latest`** and prints a bogus "deployed a minute ago" timestamp with the current block time. Never date a deploy from a `getCode` bisect on these nodes: it reads as a freshly deployed contract on one that is weeks old. Find the creation block from the deployer's nonce or an explorer API, and treat an unreadable historical block as unavailable rather than empty. Reconstruct the window from the pair's own `Swap` events instead (`0xd78ad95f…`, `amount1In`/`amount0Out` for the native side), which is also the only reading that separates real swaps from LP adds, mint refunds and the token contract's own tax `swapBack` that a plain `Transfer`-topic scan folds together and mis-reads as buyer money. Keep `getReserves()` at `latest` for current depth only, and treat any historical-state read as unavailable rather than as zero. The pair's `Sync` events (`0x1c411e9a…`) are the substitute for a price or depth history over a window, and the wallet's own `baw wallet tx-history` is the substitute for pricing a specific past swap.
- **Strip the `0x` before zero-padding a topic filter.** `"0x" + addr.rjust(64, "0")` builds a 66-character token, so every chunk answers `-32602 invalid argument 0: invalid hex string`; a scan that only accumulates `result` then reports zero transfers, which reads as "that wallet never moved anything" even after it moved the whole allocation. Pad `addr.lower().replace("0x", "").rjust(64, "0")`, and print the failed-chunk count next to the hit count so a malformed filter cannot pass as a clean scan.
- **A "404" name does not make an ERC404.** Check `decimals()` and query `getPair` on the V2 factory plus `getPool` on the V3 factory across fee tiers. If both come back empty and `decimals()` reverts, it is a plain ERC721 wearing 404 branding: no AMM, so the only exit is a marketplace bid.
- **A large `tokensPerShare` in a fair mint shrinks the dump curve; compute before reusing the exit-liquidity verdict.** When the per-share token amount is tiny against the seeded pool tokens, even a full cohort dump returns tens of percent of entry rather than cents, so quote the per-share payout at 0 / 1000 / all-sellers and the absolute cap on what can ever leave (the pool's whole quote reserve, not the FDV). The free-claimers-are-the-exit story is a calculation, not a default.
- **A launch-price multiple is a formula, not a promise.** A constant like `LAUNCH_PRICE_MULTIPLE = 2` derives `tokensPerShare` so the seeded open price is exactly N x mint price; say that the 2x exists only if a buyer takes the other side of a one-pair pool, and pair it with the refund branch (unfilled by deadline returns `refundBps`, e.g. 80%, rest to treasury) as the real downside bound.
- **An alert nobody can act on is noise, and eligibility is per project.** Every sibling deploys its own `identity()` wrapper, so a wallet can be eligible on one mint and a zero on the next; check the current contract's own gate, not a remembered verdict, and put the per-wallet result in the message so the user knows whether to move.
- **`identityOf` reverting on the gate contract usually means you called the registry, not the gate.** SPACE ID's handle registry exposes `handleOf(address)` (string) and `ownerOf`/`ownerOfHandle` only; an empty handle is "no ID". A zero ID from the wrapper, or a revert on the registry, is a wrong-address signal before it is a "gate broken" signal. Some project wrappers omit `identityOf` entirely and only expose `handleOf` plus `balanceOf`, so try the handle read before concluding the gate cannot answer.
- **A dynamic argument needs an offset word, not zeros in its slot.** `eligibility(addr, "")` encoded as `addr || 0×32` reverts with a bare `0x`; a `string` param sits behind a head/tail pointer (`addr || 0x40 || len || data`). Encode it or a healthy contract reads as broken.
- **When `identity()`/`gate()`/`registry()`/`treasury()` all revert, pull the addresses out of the runtime bytecode.** Walk the code for **both** PUSH20 (`0x73`) and zero-padded PUSH32 (`0x7f`) constants, call `name()` on each one, and treat a constant sitting in a `7f<addr>6001600160a01b03165a` run (push address, GAS, CALL) as the payment destination: that is why `eth_getBalance(mint)` stays 0 while paid mints keep landing, so say "proceeds forwarded per tx", never "funds locked". `trace_transaction` does not exist on public BSC RPCs, so bytecode context is how the routing gets proven. A `0x73`-only scan returns **zero** addresses on solc 0.8.x optimized output, because an address constant is stored as a 32-byte push with 12 leading zero bytes; reading that empty result as "no hardcoded addresses" misses the payment destination that is right there in the code.
- **Do not enumerate a contract's functions by scanning for `PUSH4` followed by `EQ` (`14`).** That heuristic matches every 4-byte constant in the runtime code, including error selectors and inline data, so a 17 kB mint reported dozens of "selectors" where only a handful were real dispatch entries, and reading the extras as live functions invents an admin surface that does not exist. Compute the selectors for the names you actually care about (`owner()`, `pause()`, `withdraw` in both arities, `upgradeTo`, `transferOwnership`, `setPrice`, `sweep`, `rescue`) and grep the raw bytecode for those specific 4-byte strings; confirm any hit is a real entry by the `63<selector>1461<dest>57` dispatch shape. Absence of all of them is a credible "immutable, no owner", presence of one is what leads the report. The same caution applies in reverse to the candidate list: extracting the `63<sel>14` dispatch constants is a legitimate **discovery** step for an unverified mint's reads (resolve them by name through 4byte.directory, then keep only the ones a live `eth_call` decodes), but a constant that only ever appears inline in the code — error selector, string fragment, jump table value — must never be reported as a function just because it survived the scan.
- **A screener `has_withdraw: true` can be an interface, not an owner path.** The flag greps `withdraw`, so a fair mint that unwraps WBNB during refunds (`IWBNB.withdraw`) trips it while the contract exposes nothing but `start()`. The bundled screener now strips `interface` blocks before flagging and prints `withdraw_funcs` with the names it matched, so a hand grep is the only remaining way to repeat the mistake: match `function .*withdraw` inside the contract body and list the real owner-only functions before telling the user a mint is owner-withdrawable.
- **Not every fair mint exposes `deadline()` or `mintingOpen()`, and their reverts read like a broken probe.** On the constant-based template the window is `startedAt() + MINT_DURATION` and the single view is `info()` returning `(phase, sold, freeClaimed, deadline, raised)`. Read `info()` first and derive the phase from its first word; the per-wallet reads there are `freeAllocation(addr)` / `paidSharesOf(addr)` / `mintedById(bytes32)`, not `freeAvailable` / `mintedBy`.
- **`baw wallet address --json` returns six chains with Solana at index 0.** Select `data.addresses` where `binanceChainId == "56"` for BSC; reading the first entry hands you a Solana base58 string that every EVM call then rejects. All EVM chains share one address on this wallet, so a BSC miss is a wrong key, not a wrong chain.
- **A struct view that returns strings has its fields shifted.** For `info()` returning `(string,string,...)`, word 0 is the offset to the struct; every later field sits relative to that struct start, so field k is at word 1+k after skipping the two string pointers. Reading words in absolute order silently assigns the treasury to `quote` and the pair to `native`.
- **595 log rows can be 418 humans or one bot army.** Recompute the participant count from `Minted`/`FreeClaimed` logs: distinct payer addresses, distinct IDs, and shares per payer. 4444 free claims from 4444 distinct handles against 418 paid wallets reads as free-allocation farming, and those wallets are the first sellers at launch.
- **A per-wallet quota view is not a gate verdict, and neither is a zero quote.** `freeLeft(addr)` coming back at the wallet maximum (or `freeAvailable(addr) == true`) alongside `quote(addr, 1)` returning 0 says the quota is untouched and the units are priced at zero; it says nothing about whether the call will pass. On an Agent-ID-gated ERC721 the same two reads were green for a wallet whose `mint(1)` reverted with a custom error, while the gate contract's `balanceOf` for that address was 0 and 1 for the eligible lane. Only simulating the mint calldata from the signing address settles it, so never tell the user "kamu masih bisa 2 free mint" from the quota read alone.
- **A reverting `eth_call` of the mint function is a positive result, not a broken probe.** An unverified mint has no ABI to decode custom errors against, and an unresolved selector from `eth_call` (a bare `0xf947691f`) is still proof that the call was rejected for that wallet while an identical call from another wallet returned `0x`. Pair it with `eth_estimateGas` from the same address: a clean estimate (returning a plausible gas figure) plus a clean `0x` return is the eligible case, and gas sizing falls out of the same round trip.
- **`handleOf(addr)` reverting on the mint contract is not a gate failure.** A contract may declare the getter it delegates to without binding the user's wallet, so it reverts for everyone including the eligible lane; read the gate contract's own `balanceOf` (and its own handle getter) per wallet instead, and treat a shared revert as "wrong read", never as "nobody qualifies".
- **Marketplace/explorer pages are not the ledger and are often unreachable.** BscScan contract pages refuse extraction from this host (Cloudflare challenge, `Upstream forbidden`), so a bare-address free-mint check is answered entirely from public RPC: `eth_getCode` to confirm a contract, then `eth_call` for each recovered selector. Say which source each number came from rather than implying the explorer confirmed it.
 When the address is an `indexed` parameter it lives in a zero-padded topic word (`topics[1]` for `FreeClaimed(address indexed wallet, bytes32 indexed id, uint256 n)`), while `data` carries the non-indexed fields, so slicing an address out of `data` collapsed 800 distinct claimers into one "distinct wallet" and would have been reported as a single actor. Read addresses from the topic words (`'0x' + topics[k][-40:]`), and when the event has no ABI, group a contract's logs by `topics[0]` first: the busiest topic whose row count equals a known cap (800 rows against 800 free shares) identifies the event and its indexed slots without it.

- **An address in a screenshot is truncated.** A UI shows `0x620FdE72...109F5f` and nothing more, so it cannot be prefix-matched, resolved or searched against known lanes. Ask for the full address before making any claim about whose wallet it is, and never infer ownership from the visible prefix.
- **A chain name in viem's built-in list can be a different project's chain.** `viem/chains` exports `elysiumTestnet`, but that is Vulcan Forged's Elysium (chain 1338, gas token LAVA); Kinetiq's Elysium is the HYPE-gas one, mainnet ID 99800 (`https://rpc.elysium.kinetiq.xyz`) and testnet ID 99801 (`https://testnet-rpc.elysium.kinetiq.xyz`), so name the network and its ID together instead of writing "Elysium" alone. Take the chain ID and RPC from the project's own docs or from the `defineChain` block in its site bundle and `defineChain` it yourself: a matching built-in name quietly sends every call to an unrelated network.
- **Testnet volume priced at today's mainnet token price is free money, not traction.** An explorer that converts test gas-token flow at the live mainnet price reports huge "volume" funded by a faucet; never quote it as demand.
- **`import 'viem'` fails from a script living outside `~/.hermes/web3-harness`.** ESM resolves packages relative to the script's own path, not the cwd, so a probe parked in `~/.hermes/cache/scratch` dies with `ERR_MODULE_NOT_FOUND: Cannot find package 'viem'` even when launched with `cd` into the harness. Resolve it explicitly: `const require = createRequire(path.join(HARNESS, 'package.json')); const { createPublicClient, http, formatUnits } = require('viem');`, which also makes the probe runnable from anywhere. RPC URLs come from the same harness `.env` (`BSC_RPC_URL` etc.).
- **`~/.hermes/state.db` is locked while the gateway runs.** `sqlite3 ~/.hermes/state.db` answers `database is locked (5)`; copy the file to scratch and query the copy to recall a past turn (session ids, role, content). Use it to find which wallet did which action before re-verifying that action on chain.
- **A reusable probe parked in the scratch directory disappears.** `~/.hermes/cache/scratch` is pruned when idle, so a later call to a script that lived there dies with `No such file or directory` while the numbers it printed were correct when it ran. Keep anything a future session or a job re-runs (alert poster, calldata builder, price reader) in `~/.hermes/scripts/` and rebuild a lost one there: a price reader must compute from the pair's own `getReserves()` and router quote with the USD leg from an on-chain stable pair, so it cannot be replaced by a bare web quote.

- **An indexer's price is not the ledger on a fast-moving pair.** DexScreener's `liquidity.base` / `liquidity.quote` lagged the chain by 10-20% during a live pump, so fiat figures converted from it came out too high twice in one session. Convert from the pair's own `getReserves()`, and confirm the pair's token and native `balanceOf` match those reserves so a donation is not skewing the quote; the same applies to the pool-depth figure in the verdict.
- **Never date an emission halving off a short pace sample.** A 90-second `totalShares` delta read 8,640 shares/hour where two hours of the minter's own `MintFree` / `MintPool` logs gave 5,327, which moved the quoted halving ETA from 4 hours to 19 and forced a retraction to the user. Sum `shares` from the mint logs over 1-2 hours, divide by the block-timestamp span, then apply `EPOCH / rate`; if only a 90-second delta is available, quote it as an upper bound and say so. The same short-sample noise governs a sell-out ETA: successive instantaneous `paidShares` deltas minutes apart swung between roughly 1,300/h and 220/h, so quote a range derived from multi-chunk counts and label it pace-dependent, never a single rate.
- **A soulbound, signature-gated identity NFT turns a free mint into a closed set, not a gate you can buy into.** When the eligibility asset cannot move (`_update` reverts `Soulbound`, `approve` / `setApprovalForAll` revert, minting needs an off-chain signer signature, one handle per address), there is no floor price to quote and no secondary market to scale through: check `balanceOf` per address, say the gate is unpurchasable, and state that scaling means onboarding more eligible addresses. It also pins the claim, because the ID cannot be moved to whichever wallet holds the gas, so the mint and the claim must run from the address that already holds the ID. Only that is pinned: the token that lands there is freely transferable, so the sell runs either from that wallet or from any funded wallet the token is moved to, and the untaxed wallet-to-wallet transfer plus one extra tx is a legitimate way to sell from a cheaper-gas lane.

- **Strip the `0x` before slicing an `eth_call` return into 32-byte words.** Slicing the raw hex string in 64-char chunks folds the two prefix characters into word 0, so every field lands shifted by one byte: `phase` reads as 0 and a timestamp decodes to a number that overflows `time.gmtime`. Do `b = res[2:]` then `[b[i:i+64] for i in range(0, len(b), 64)]`, count the words against the ABI's return list, and sanity-check word 0 (an enum phase, a boolean, a small counter) before trusting the rest of the tuple.
- **BSC produces a block roughly every 0.45s, so convert hours to blocks with the live ratio, not a remembered 3s.** Measured 37,188 blocks across 4.6h. Assuming 3s makes a 6h lookback window ~7x too wide (slow, and more chunks to fail on) and turns "last 2000 blocks" into a few minutes of history. Sample two block timestamps and divide before picking a `fromBlock`, and prefer deriving `fromBlock` from the mint's own `startedAt` by binary search over `eth_getBlockByNumber` timestamps instead of guessing an offset.

## Reporting Shape

For this user's preview channel: casual Indonesian, no em dashes.

1. One bold verdict line that answers the question in a single sentence.
2. A short block of what is genuinely fine (contract verified, no admin, bounded approve, gate is a real NFT).
3. A short block of what makes it risky, each bullet carrying one hard number or address.
4. A recommendation line: skip, free-claim with gas only, or proceed, plus the specific approval caveat.
5. When the question is "butuh berapa lama", answer three clocks separately: transaction confirmation (a few seconds on BSC), time left in the mint window (`startedAt + MINT_DURATION`, quoted in WIB), and the sellout ETA implied by the observed paid pace. When that pace makes the cap unreachable, say the refund branch is the realistic outcome and name its haircut, instead of implying the mint will eventually fill. On a refundable-deposit lane the exit clock is per position (mint timestamp + `REFUND_DELAY`) and the daily quota clock rolls at 00:00 UTC = 07:00 WIB, both separate from the trading-open time; quote them in WIB and say that minting either side of 07:00 WIB banks two quota windows in one WIB day.
6. When the user takes the free-claim path, a separate short check-in before signing: eligible yes/no with the gate asset, exact gas in native units plus fiat, unlock date, and the one action still blocking execution (e.g. Developer Mode off).

7. When the user asks "kenapa turun terus" or suspects a bundle, lead with flow arithmetic rather than chart talk: net sell versus buy from a 60-90 second swap window, distinct seller count with the top-1 share, and the deploy-destination wallets' token outflows over recent blocks. Then state "no single entity" explicitly, and give the ratio that explains the move (net sell size against the pool's quote reserve), because on a thin pool a few thousand dollars of net selling is the whole story.

9. On a bare repeat price check ("berapa harga 1.4M AGC sekarang?"), answer with the number first and nothing in front of it: the realisable figure for the position size, then the unit price and pair reserves, then the trend against the last check. Keep it short, and add the held-position value plus the refunded-deposit line only when the user is deciding about an exit; do not re-run the audit verdict on every check, and when a check lands after a scheduled exit already fired, verify the round trip on chain and report it in the same reply rather than answering the price alone.

9. When the user asks for a multi-day payout ("berapa payout hari 1-5"), split the answer in two columns and keep them apart: the token amount per day is contractual (quota ladder x the stage base each mint lands in) and can be stated flatly, while the USD payout is a price assumption and must be a scenario table, not a number. Give three sale-price paths (flat, -20%/day, -50%/day), name the day where the payout no longer covers gas as the stop day, and repeat that the sale happens at claim time a day out, so the mint-time price is not the number. One dollar figure for a multi-day projection is a price assumption dressed as a forecast, and the user will hold you to it.

10. On a repeat status check of a mint the user already holds ("coba cek lagi, naik atau turun?"), answer with the counter, its direction and the net rate first, then the comparison against your own previous reading (give the series of timestamps you recorded, so the trend is checkable), then one line on whether the exit plan is still armed. Do not re-run the audit or restate the exit math: the number being asked for is the delta since last time. Close with the plain consequence (sell-out approaching, receding, or stalled) rather than a fresh verdict.
