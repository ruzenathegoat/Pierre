# Ecosystem / Testnet-Points Reconnaissance

Use when the user drops a project or a whole ecosystem as hype ("lagi rame di grup telegram, cek dong") that is NOT a single priced mint: a testnet app with a points program, an app suite (marketplace + launchpad + DEX + social), a chain whose mainnet is about to launch, or a pre-mainnet mint whose terms are still unpublished. The deliverable is a verdict the user can act on plus a numbered setup checklist, and the honest answer is often "produknya nyata dan jalan, tapi tokennya belum ada".

## Procedure

1. **Render the app, then grep it.** Pull `document.body.innerText` for the first-screen shape (marketplace / DEX / launchpad / all-in-one) and the testnet banner, then grep the rendered HTML for `/api/` paths, the project's data/API host, and `0x[a-fA-F0-9]{40}` addresses.
2. **Find the project's own data API: it is the richest source and needs no wallet.** Apps in this space ship a JSON host (e.g. `data.<domain>/v2/...`). The high-value paths: `points/status` (program state, target day), `launch/drops` (every drop's contract address, `templateVersion`, `seaDrop`, `feeRecipient` + `feeBps`, and per-stage `priceWei`/`start`/`end`/`maxPerWallet`/`stageSupply`, plus `totalSupply`/`maxSupply`/`hasMinted`), `dex/airdrop/config` (`distributor`, `owner`, an embedded `abi`, and flags like `independentlyAudited` and `testnetOnly`), and `daily-token-rewards/config` (token address, decimal, daily budget, staking vault, publisher, program id, and `startDay`, the program's true start date). Probe the obvious paths and print the HTTP status per path: a 404 is informative and costs nothing. For "sejak kapan farming-nya jalan?" answer with that `startDay` plus the chain testnet's launch date, never with the app's "just launched" copy, and say whether points carry over (they usually do not, so days already missed can never be recovered).
3. **Read the chain's own ecosystem listing** (`<l2-explorer>/ecosystem/<project>`) for the project's contract list with per-contract transaction and user counts, plus the project's 7d volume/TVL. Read the footnote: those dollar figures price the testnet gas token at TODAY'S mainnet price, so a faucet-funded testnet reports millions of "volume" that means nothing.
4. **Verify on chain, never from the page.** `eth_chainId` first, then `eth_call` `name()` / `symbol()` / `totalSupply()` on the project token, then `eth_getCode` on the marketplace and router to prove they exist. `totalSupply` is the number every later claim hangs on.
5. **Compute the valuation the asking price implies.** `(mint price × units) ÷ (fraction of total supply promised)` gives the FDV the seller is setting. A $25 mint for 1,500 units where the collection is promised 10% of a 1B supply implies roughly a $375k FDV. Quote it next to the mint price; it is usually the smallest number in the report and it answers "is this cheap?" without endorsing a price.
6. **Read the whitelist mechanics literally and quote them:** GTD versus FCFS, the cut-off (e.g. "profile #1 to #1000"), and the definition of "active" (usually an on-chain action inside a rolling window, often 7 days). Cross-check the leaderboard's top join numbers to see how far past the GTD cut the user already is; a 49,000-number leaderboard means an early joiner is FCFS, not GTD. **GTD is a guaranteed ALLOCATION, not a free mint:** the tiers usually carry the same price, so say "slot dijamin di harga $X" and never let a guaranteed slot read as free. When the site shows a single price and no per-tier split, the tier prices and the per-wallet cap are unpublished, so say that rather than assuming a discount, and present any derived FCFS slot count (total supply minus the GTD cut) as your own arithmetic, not as an official number.
7. **Cross-check the mint date against the chain's own mainnet date.** A pre-mainnet mint (the mint lands before the chain the token lives on exists) almost always means payment currency, mint chain and per-wallet cap are NOT published yet. That gap is the risk to flag, not a detail to gloss, and it is the reason to tell the user to wait for the official post before sending real money.

## Pitfalls

- **A chain name in viem's built-in list can be a different project's chain.** `viem/chains` exports `elysiumTestnet`, but that is Vulcan Forged's Elysium (chain 1338, gas token LAVA); Kinetiq's Elysium is the HYPE-gas one, mainnet ID 99800 (`https://rpc.elysium.kinetiq.xyz`) and testnet ID 99801 (`https://testnet-rpc.elysium.kinetiq.xyz`). Take the chain ID and RPC from the project's own docs or from the `defineChain` block in its site bundle and `defineChain` it yourself: a matching built-in name quietly sends every call to an unrelated network.
- **Testnet volume priced at today's mainnet token price is free money, not traction.** An explorer that converts test gas-token flow at the live mainnet price reports huge "volume" from a faucet; never repeat it as demand.
- **A marketplace listing/approval covers the whole collection and survives the trade.** Tell the user to farm any testnet app from a wallet holding nothing of value, and that the project cannot withdraw the approval for them.
- **"Points" with no confirmed token is the normal state, not a bug.** Anonymous team, no ToS, and contracts flagged `independentlyAudited: false` are the baseline for these apps. Say so plainly and never imply the points will pay.
- **Testnet collections cloned from blue-chip names (BAYC, Azuki, Pudgy, CryptoPunks, Milady) and deployed by the project's own wallet are a quality signal, not a tie to the real collection.** State which wallet deployed them so the user is not misled by the name.

## Off-chain whitelist application forms

When the gate is a form rather than a token, the audit is: what does the form ask, who can complete each step, and what is the WL actually worth. Report-only by default, and submit nothing until the user says go.

1. **Read the form's own route chunk, not the marketing page.** "Apply for WL" is a route (`/whitelist`), and on a Vite/React build that route's code lives in a separate chunk: fetch the site's main bundle, grep it for the lazy import map (`import("./<Route>-<hash>.js")`), then fetch the chunk for the route. The step labels, the question text, the validation rules (minimum answer length, duplicate-handle check) and the POST target with its payload keys all sit in that one file, e.g. `const T=["X account","Wallet","Follow","Like + Repost","Tag","Your answers","Review"]` and `post("/api/wl-apply",{collection,x_handle,wallet,why,contribute,tasks:{follow,engage,tag}})`. Read the payload keys literally: they are what the backend scores.
2. **Enumerate the steps and mark each one's owner.** Any step performed on X or inside a wallet belongs to the user. The agent has no X account and cannot follow, like, repost or reply-tag, so those are the user's to complete and the agent must never claim them. Submitting with those steps unverified burns the single application the identity is allowed, so when the user has not done them, say which steps are theirs and wait.
3. **State the one-per-identity rule before anything is submitted.** These forms normally allow one application per wallet and per X handle and answer a repeat with the existing application number; there is no second attempt.
4. **Read the status endpoint instead of re-submitting.** These builds carry `GET /api/wl-status?<wallet or handle>`; use it for the state report, and never fire a synthetic application to see how the backend behaves.
5. **Price the WL against the mint's live state.** Read the mint counters: when the public phase is already open with supply left, the WL buys priority, not access, and the honest line is "ini bukan tiket masuk, cuma antrian". Add that a free mint on another chain still needs that chain's gas token, which usually means a bridge, so "gratis" covers the mint price only.
6. **Check what the wallet step is scored on.** One step scans a wallet for activity on a named chain and sets the tier from it, so a wallet with no history there scores the floor no matter how good the written answers are. Name the wallet to use and say what a zero-history wallet scores. Note an odd weighting (a project on one chain scoring activity on another) as a signal, not a defect.
7. **Manual review is not a queue position.** A submitted state plus "you are in the queue" is a review verdict, not a guaranteed allocation and not a payment; say that when the user reads the receipt back.

## Reporting Shape

Same casual-Indonesian, no-em-dash shape as the main skill, but the tail is a setup plan:

1. Verdict line: is the PRODUCT real (verified on chain), and is the TOKEN/airdrop confirmed (almost never).
2. A block of what is verified on chain: addresses, chain ID, the project token's real supply, and the one computed number (implied FDV).
3. A block of red flags, one hard figure each (supply versus mint price, anonymous team, unpublished mint terms, clone collections).
4. A numbered setup checklist for joining, split into "what I can prepare" versus "what only you can do". Connecting a wallet and signing happen on the user's side; the agent can supply network parameters, the faucet URL and reminder jobs, and nothing that needs a signature.
5. Offer concrete follow-ups rather than a bare report: a `no_agent` reminder cron for the daily action, and/or an announcement watch for the still-unpublished mint terms (currency, chain, per-wallet cap).
